# Dispatch-seal catalogue transition

This component installs the schema protection needed by a future old-source dispatch seal. It does not issue a seal, fence role effects, establish provider drain, reopen a source, or make roles reusable.

`schema/dispatch-seal-predecessor-160.json` preserves the exact accepted pre-seal catalogue (SHA-256 `287668140aff83df1fc0ae757e77d87f733a6e67dc8365eb7db2e31ae6a7533e`). Both layouts retain all 69 application tables, 84 explicit indexes and 221 triggers. The target adds only three fixed semantic triggers; all original 13 semantic trigger bodies are unchanged. The complete catalogue grows from 442 to 445 objects, and the trigger count becomes 224.

The explicit `current-cookie-pre-seal` source kind accepts only that preserved predecessor. Both the direct closed-profile capture and the same-original writer-fence capture execute one atomic group: complete source proof, three exact `CREATE TRIGGER` statements, the original nine-field epoch CAS, and complete target proof. There is no table rebuild, business data write, birth initialization, trigger removal or in-place serving upgrade. Existing typed data, rowids, sequences, all six raid fields, pending/unknown role custody, and any permitted recorded-layout companion remain unchanged. `legacyDelayedFieldsNull` is false because existing values are retained.

`current-cookie` continues to mean the exact new target and performs only its original epoch transition. Serving admission accepts only the new target. The predecessor is not an alternative serving profile. The receipt and link validators bind the distinct full predecessor/target digests, including the same optional recorded-layout companion on both sides. Captures remain one-use and retain their original 300-second clock, original control tuple, Native method/result custody, query limits, and independent close/opener requirements.

The generated legacy-source JSON export remains byte-identical. A separately named predecessor-source export keeps each parsed constant below the existing 2 MB bound; the parser and SQL/binding limits are unchanged.

Once `betaResetDispatchSealV1` exists, the three new triggers prohibit replacement, key rename, deletion and changes to the value or timestamp of that setting and of `betaResetPolicyV1`. The sole update exception allows the existing erasure statement to clear a non-null `updated_by` while retaining the exact key, value, timestamp and their SQLite types. Attribution cannot be reassigned, and an already-null attribution does not authorize a no-op update. Presence is sufficient: malformed seal contents still enforce these rules. The initial seal insert is not itself authorized by these triggers; a future issuer must supply its own source-owned proof and atomic CAS. Before any seal exists, normal policy writes remain possible. Unrelated admitted settings remain writable afterward.

Run the focused local regression with `npm run test:dispatch-seal-profile`. It uses the existing real Native/private-control fixture graph, tests both layouts and both capture paths, preserves nondefault values, injects transactional failures after every transition step, rejects stale schemas/control/deadlines, validates receipt digests, and attempts mutations through the actual admitted writer. A fixture-only mode change used to exercise installed semantics is not a production opener.

This source change leaves `roleReuseReady`, provider drain, all-writer drain and production activation unqualified. The historical live census showed five never-dispatched queued role rows and no observed dispatching/unknown rows; it did not drain already-dispatched or receiptless effects. A future seal must separately establish its installed source barrier and cutoff/retirement predecessor. No armed policy, original policy digest, provider ACK or restore barrier may be manufactured from this migration.
