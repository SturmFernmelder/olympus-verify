# Olympus audit — Discord server, MEE6, olympus-verify

Date: 18 September 2026. Scope: the Discord server's roles and channel permissions, the MEE6
configuration, and the olympus-verify application (Worker, watcher, addon). Everything below was read
from live state — the deployed Worker, the running watcher, the MEE6 dashboard and the Discord client —
not from the design documents.

## 1. What is live right now

`GET /health` returns build `2026-09-18.9 guide-buttons-auto-admission-chatlog-events`, `mode: auto`,
all six secrets present, D1 reachable, Battle.net login enabled, Phase 3 off with no namespace. The
source tree on the PC is at the same build, so nothing is waiting to be deployed. All four commands are
registered (`/verify`, `/verify-status`, `/olympus-admin`, and the "Olympus linked characters" user
context menu), and the pinned guide with its three buttons is live in #join-guild.

The watcher is running: its state file was written 30 seconds before this check. The last roster export
was received at 12:34 local, about four hours before the audit, which is the natural cadence of an
officer's `/reload`. The addon source is 0.2.0. The installed copy under `D:\...\_classic_beta_` could
not be inspected from here because only the OneDrive folder is mounted, so the addon version actually
loaded in the client is the one unverified piece of the chain.

Both offline test suites pass: the watcher's eight Python tests, and the addon harness (run against
stubbed WoW APIs). The Lua HMAC was additionally checked against all eight vectors in
`watcher/tests/vectors.json` and matches.

## 2. Findings, most severe first

### A1. A player can forge a guild join and be granted Guild Member

The watcher distinguishes a server system line from a player's message only by the absence of a colon
(`watcher.py:40`, `GUILD_JOIN_RE`). An emote renders in `WoWChatLog.txt` as `<Name> <text>` with no
colon, so `/e has joined the guild.` produces a line byte-identical to the real system message. The
Worker acts on it at once: `ingest.ts:113` promotes any character whose status is `verified` or `queued`.

The result is that anyone who has completed `/verify` and whispered a valid code — but has never been
invited and never joined — can stand next to the officer, emote that sentence, and receive the Guild
Member role. That defeats the roster check the whole pipeline exists to enforce. The parsing gap is
confirmed; exploitability depends on the exact emote rendering in the log, which could not be tested
without the client, so treat it as very likely rather than proven.

The mirror case, `/e has left the guild.`, reaches `demote()` but only for the emoter's own name, so it
is self-harm and not a concern.

The fix is to stop trusting the log text for membership transitions. The addon already sees
`CHAT_MSG_SYSTEM` itself (`OlympusVerify.lua:538`) and can distinguish a genuine system message from a
player emote, because the client delivers them on different events. Make the addon the authority for
join and leave events, or require a roster snapshot to confirm a join before the role is granted.

### A2. A truncated roster export strips Guild Member from everyone missing

`ExportRoster` loops `1..GetNumGuildMembers()` (`OlympusVerify.lua:214`) and never calls
`SetGuildRosterShowOffline(true)` — a grep of the whole addon confirms the call appears nowhere. On
Classic-line clients `GetGuildRosterInfo(i)` indexes the *displayed* roster, so with "show offline"
unchecked the loop stops at the online count. The probe recorded 450 total and 422 online on the beta,
so a typical export would carry 422 of 450 names.

Nothing on the receiving end notices. `ingestRoster` (`roster.ts:88`) walks every name in the previous
snapshot that is missing from the new one and calls `demote()`, which removes the role. There is no
minimum member count, no maximum shrink ratio, and no comparison against the previous snapshot's size.
One truncated export removes the role from twenty-eight people at once, with twenty-eight DMs and
twenty-eight log lines.

This is the single largest risk in the system, and it sits directly underneath the automatic-removal
behaviour discussed in section 3. It needs two fixes: call `SetGuildRosterShowOffline(true)` before
exporting, and add a guard in `ingestRoster` that refuses a snapshot which is more than, say, ten per
cent smaller than the previous one unless a flag overrides it.

### A3. Discord deletes Battle.net connections from the API on 22 September

Discord's developer changelog entry of 14 August 2026 states that newly created Battle.net connections
are already excluded from `GET /users/@me/connections`, and that from 22 September 2026 existing ones
will be excluded too, with no replacement. That is four days away.

The design already anticipated this: `/linked-role` falls through to Blizzard's own OAuth when no
verified Battle.net connection is returned, and `/bnet/link` reads the BattleTag from Blizzard's
`userinfo`. `bnetLogin` is `true` in `/health`, so the fallback is configured and working.

There is still a defect. The fallback only triggers when Discord returns a *successful* connections list
that happens to lack Battle.net (`oauth.ts`, the `if (!bnet)` branch). If the connections call returns a
non-OK status or something that is not an array, the handler returns a 502 page and the user is
dead-ended with nothing saved. Since the connections request is now pure overhead, the cleanest fix is
to drop `connections` from the requested scopes and go straight to Blizzard's login. That also removes a
permission from the consent screen that members currently grant for no reason.

### A4. A Worker outage loses events permanently

Every ingest path except the roster marks an event as seen *before* posting it and never rolls back
(`watcher.py:156`, `watcher.py:162`, and the SavedVariables path at `watcher.py:208`). `Worker.call`
returns `None` on a 4xx without retrying — which includes a wrong `watcher_token` producing a 401 — and
`None` after three retries on 5xx or an unreachable host. No caller checks the return value.
`tail_chat_log` advances the file offset unconditionally, so the line is never re-read either.

This was reproduced end to end against a stubbed-down Worker: a verify and a guild join attempted while
the Worker was down were recorded as seen, and after a restart with the Worker up, nothing was resent.
`forward_roster` is the only path that gets this right — it advances its watermark only when the call
returned something — which strongly suggests the others are an oversight rather than a decision.

The member-facing symptom is the worst kind: the addon whispers back "code confirmed, invite queued",
and then Discord does nothing, forever, with no error anywhere. In Lean terms the line does not stop
when a defect occurs; the defect passes downstream invisibly. This should be fixed before any effort is
spent making the pipeline faster.

### A5. MEE6 holds Administrator

The MEE6 role carries the Administrator permission. Administrator bypasses every channel overwrite,
including the read-only locks applied to #join-guild and #help-desk, and grants server management,
audit-log access, invite management and message deletion everywhere. It is the largest standing
third-party privilege on the server.

MEE6 needs none of it for what it is actually configured to do: an audit log, a ticket panel, levels,
reaction roles, custom commands, and two social alerts. Manage Roles, Manage Messages, View Channels,
Send Messages, Embed Links, Read Message History, Add Reactions, Manage Threads, Kick, Ban and Timeout
would cover every enabled feature.

Note also that the MEE6 role sits at position 14, below Guild Member at 15. Administrator does not
bypass role hierarchy, so MEE6 cannot time out, kick or ban anyone who holds Guild Member — which is
every member of the guild. The bot therefore has enormous permission and no ability to moderate the
people it would need to moderate. Both halves of that are wrong: reduce the permission set, and move the
MEE6 role above Guild Member if you want it to moderate members at all.

### A6. The welcome DM told every new member to do something impossible — fixed

MEE6's Welcome & Goodbye plugin sends a private message to every new member. Until today it read
"Request guild access: … include character, ruleset/faction, class and main/alt. An Officer verifies
in-game membership before granting Guild Member", and "The welcome area is public. After approval, use
#guild-chat …". Since yesterday's lockdown, new arrivals cannot post in #join-guild at all, so the first
instruction a new member received was one they could not follow. It also carried two references to
Fernmelder and a line about waiting ten minutes before posting that no longer applies.

This has been rewritten and verified: it now points at the pinned guide, explains that Guild Member is
granted automatically once the character is on the roster, states plainly that #join-guild and
#help-desk are read-only, and names richwcampbell as the fallback contact.

For completeness, the other toggles on that plugin are: public join message off, welcome card off, join
role off, leave message off, captcha off. Only the DM is active.

### A7. Double logging into #server-log

MEE6's audit logging writes to #server-log with "Member roles changed" and "Nickname changed" enabled.
olympus-verify writes its own line to the same channel on every promotion and demotion, and it also sets
the nickname. Every admission therefore produces three entries in one channel: the bot's own line, a
MEE6 role-change line, and a MEE6 nickname line. Point MEE6's audit log at a different channel, or turn
off those two events, so #server-log stays readable when something goes wrong.

### A8. MEE6's automod is entirely disabled

The Moderator plugin is switched on, but every rule underneath it — bad words, repeated text, server
invites, external links, excessive caps, emojis, spoilers and mentions, zalgo, anti-spam — is Disabled,
there are no automated actions, and no restricted channels. Immunity is set to the MEE6 role only.

That is a deliberate-looking configuration only if you know Discord's native AutoMod is carrying the
load instead; #mod-alerts exists and its pinned intro describes Discord AutoMod matches, so that appears
to be the intent. Worth confirming, because as it stands the MEE6 Moderator plugin contributes nothing
but the audit log.

### A9. The bot cannot grant the Officer role

The Olympus Verify role sits at position 16. Officer is at 18, Moderator 19, Guild Leader 20, Guild
Master 21. Discord refuses to add or remove a role at or above the bot's highest role, so the bot can
grant Guild Member (15) and nothing else. This is the binding constraint on the officer-rank question in
section 3.

The bot can still *remove* Guild Member from a staff member, because removal is gated on the role's
position, not the target's. Nicknames are different — those require the bot to outrank the member — so
`setNickname` fails silently for anyone holding a staff role, which the code already handles by auditing
`nick.failed`.

### A10. The bot does not recognise the Guild Master role

`cmdAdmin` and `cmdUserMenu` gate on `ROLE_OFFICER`, `ROLE_MODERATOR` and `ROLE_GUILD_LEADER`. There is
a separate role named **Guild Master** (id 1549892601170108416, position 21, carrying Manage Server and
Manage Roles) that the Worker knows nothing about. Anyone holding only that role is refused by every
admin command. Either add it to the gate or fold it into Guild Leader.

### A11. Smaller application defects

A zero-byte chat log re-arms the first-run branch, so the first poll after the log is truncated jumps to
the end and silently drops whatever was written in between (`watcher.py:122`). It self-heals after one
poll, but recurs every time the file is truncated.

Log rotation is detected by size alone — there is no inode or fingerprint check — so if the log is
recreated and grows past the old offset before the next poll, the watcher seeks into the middle of the
new file and skips everything before that point.

The queue writer escapes backslash, quote and newline but not carriage return (`watcher.py:291`). A
single CR in a character name or note makes `OlympusQueue.lua` a syntax error, `MergeQueueFile` returns
zero silently, and every Discord approval stops arriving with nothing in the log to say why.

`generatedAt` is inside the hashed queue body (`watcher.py:297`), so the `queue_hash` dedupe can never
match and the queue file plus state file are rewritten on every poll forever.

A guild join seen both by the addon (`MemberExistsByName`) and by the chat log produces two different
dedupe keys, so it is posted twice; the role is idempotent but the Discord log line and audit row are
duplicated. The whisper paths were deliberately unified this way and the join paths were not.

`ScanMailbox` calls `GetInboxText` on every mail whose subject lacks `!verify`, which marks the
officer's entire mailbox as read.

The character-name regex in the Worker, `^[A-Za-z][A-Za-z' ]{1,30}$`, rejects accented letters. If
Forever allows them on EU realms, those players cannot run `/verify` at all.

`watcher.py --check` prints a live, working verification code to the terminal, and `watcher-state.json`
stores past codes in cleartext as dedupe keys. Neither is catastrophic — a code is only useful for two
days and only for that character — but both are avoidable. Separately, the whole project lives in a
OneDrive-synced folder, which means `watcher/config.json` (VERIFY_SECRET, WATCHER_TOKEN) and the addon's
`Config.lua` are replicated to Microsoft's servers. That is worth a deliberate decision rather than an
accident. There is also no `.gitignore` in `watcher/`, unlike `worker/` and `addon/`.

### A12. Test coverage gaps

`vectors.json` is generated from `codes.py` and then used to test `codes.py`, so the cross-implementation
claim in the design document is not enforced by anything in the repo; the Lua was checked by hand during
this audit and passes, but nothing keeps it passing. No vector uses a non-ASCII character name, which is
exactly where the three `normalizeCharacter` implementations are most likely to diverge. The watcher's
`Worker.call` is stubbed to always succeed in the tests, so nothing covers the failure behaviour in A4.
`pull_queue` is never exercised, so the CR bug and the hash churn are both uncovered. Nothing tests a
truncated roster export, which is A2.

## 3. The six questions

### Should a guild kick automatically remove the Discord role?

Yes, and it already does — that shipped in build `.9` and is live. There are two paths. The watcher
relays "has left the guild" and "has been kicked out of the guild by X" from the chat log to
`/ingest/events` as a `left` event, and the Worker calls `demote()`, which marks the character `left`
and removes Guild Member when no other member character remains for that account. Independently, the
roster diff removes the role for anyone who disappears between snapshots.

Two things should change before you rely on it. The roster path must not fire on a truncated export
(A2), and it is worth requiring two consecutive snapshots to agree before stripping a role, so a single
bad export or a mid-load snapshot cannot cause a mass removal. The chat-log path should come from the
addon's own system-message handler rather than the log text (A1).

One deliberate behaviour worth knowing: `demote()` keeps the role if the account still has another
character in the guild. That is correct, and it means kicking one alt does not remove access.

### Is there a kick that also bans them in Discord?

Not from in game, and I would not try to build one. The chat log line for a routine kick and for a
ban-worthy removal is identical, so the game cannot carry the officer's intent. Anything that inferred
severity from `/gkick` would be guessing.

The right shape is to start the serious case in Discord, where the intent is explicit, and let it flow
outward. `/olympus-admin ban` already exists and does half of this: it marks the account banned in D1 so
the BattleTag cannot be re-linked from a new Discord account, cancels any queued invite, and lists the
characters still in the guild so an officer can `/gkick` them. What it does not do is remove the Guild
Member role or ban the Discord account.

I would add both, but behind a gate. Make `/olympus-admin ban` remove Guild Member immediately, and have
it post a card in #mod-alerts with a "Ban from Discord" button that only Guild Leader can press. That
keeps the destructive step deliberate and attributable, and it leaves an audit trail in a channel staff
already read. It needs the bot to be granted Ban Members, which is a real escalation — weigh it against
the fact that MEE6 already holds Administrator, which is strictly more.

The reverse direction is free and probably more valuable day to day: when someone is banned in Discord,
nothing currently tells an officer that the person is still in the guild in game. A Discord ban event
could post their linked characters to #mod-alerts so the in-game removal is not forgotten.

### Should the GUI/UI/UX be improved?

Yes, and the highest-value change is not cosmetic. Discord approvals currently reach the addon only at
`PLAYER_LOGIN` — `MergeQueueFile` runs once, at login (`OlympusVerify.lua:517`). The watcher writes
`OlympusQueue.lua` continuously, but nothing reads it again until the officer relogs or `/reload`s.
That, not the invite key press, is the largest wait in the pipeline, and it is invisible to everyone
involved. Merging on a timer instead removes an entire class of "why hasn't it come through yet".

After that, in rough order of value: add Discord autocomplete to `/verify` sourced from the latest roster
snapshot, so applicants pick their character instead of typing it and getting the name regex wrong; add
a `/olympus-admin sync` that forces a reconcile so an officer has something to do when a member reports
a problem; show the pending count in the officer panel's title so the number of key presses left is
visible without opening it; and trim the `/verify` reply, which is currently seven lines where three
would do. The pinned guide itself is good and does not need changing.

The one UX defect that was actively harming people, the welcome DM, is fixed (A6).

### Should in-game officers automatically get the Officer role?

The data is there — `roster_members` already stores `rank` and `rank_index` from every export — so this
is easy to build. I would not build it.

The Discord Officer role is not a label; it is what `cmdAdmin` and the context menu check before showing
someone every member's BattleTag and every character they have ever linked, and before allowing unbind
and ban. Deriving that from an in-game rank means anyone who can promote in game can grant access to
personal data in Discord, silently, with no Discord-side record of the decision.

It is also blocked mechanically. The bot's role is at position 16 and Officer is at 18, so the bot cannot
assign it (A9). Making it possible means moving the bot above Officer, which hands the bot the standing
ability to create officers — a strictly worse security posture than the problem it solves.

The version I would build instead is the Lean one: have the roster ingest compare in-game rank against
Discord roles and post the mismatches to #staff-chat — "Fern Melder is rank Officer in game and has no
Officer role in Discord", and the reverse. The discrepancy becomes visible immediately, a human clicks
once, and the privilege grant stays a human decision. That is the same benefit without the escalation
path.

### Can it be made to run without you being logged in?

Partly, and it is worth being precise about which parts.

Four things need the client running with the addon loaded: validating a whispered code and replying;
reading mailed codes, which additionally needs a mailbox window open; exporting the roster, which only
reaches disk at `/reload` or logout; and noticing that an invite was accepted. One thing needs a
hardware key press: the invite itself, exactly one per press, which is a client restriction measured on
the beta and not something the code can work around. Everything else — the Worker, the role grants, the
queue polling — already runs without you.

So the officer-online dependency cannot be removed today. It could only be removed by reading the guild
roster server-side, which needs a Battle.net API that does not exist for Forever yet (next question).
Given that, the Lean answer is not to chase full automation but to attack the waits and the batch size,
in this order.

Stop the line first. A4 means defects currently pass downstream silently: a member is told their code
was confirmed and then nothing happens, and no one finds out. Persist the watcher's backlog and only
mark an event seen once the Worker has acknowledged it. Nothing else on this list matters as much,
because everything else assumes the pipeline reports its own failures.

Then remove the reload. Merge the queue file on a timer rather than at login, as above. This is the
single biggest reduction in lead time available, and it costs nothing in risk.

Then reduce the batch. The panel should make the remaining work visible at a glance — how many invites
are queued, how long the oldest has waited — so clearing the queue is a two-minute deliberate act rather
than something remembered at random. This is ordinary visual management and it is most of the benefit.

Then add redundancy. A second officer running the addon halves the wait and removes you as the single
point of failure, but it needs the per-officer claims on `GET /queue` that were deferred, otherwise two
clients will both fire the same invite.

Then level the arrivals. Codes are valid for two UTC days, so applicants do not need to catch you live —
they need to know when to whisper. A line in #join-guild saying when officers are usually on, or better,
an "officer online" indicator driven by the watcher's heartbeat, lets people self-schedule instead of
whispering into the void. That is a cheap change with a real effect on perceived latency.

One measurement is still outstanding: the `LoggingChat` off/on flush that the addon performs two seconds
after a confirmed code has never been observed working in isolation. Both times it appeared to work, a
48 KiB fill or a logout could explain it. Until that is measured — log size and mtime before and after
`/olv flushlog`, with no reload for a minute — the seconds-level latency claim in the README is a
hypothesis, not a result.

### Are there new API endpoints for WoW Classic Forever?

No. Forever was announced at BlizzCon on 12 September, its beta opened on 17 September, and it launches
on 4 November 2026. There is no published profile namespace, no guild roster route that would work for
it, and no Blizzard statement either announcing one or ruling one out.

Two corrections to earlier assumptions are worth recording. Blizzard does maintain Classic profile APIs
as a documented product line, and the guild roster route does work for Classic Era under
`profile-classic1x-us`; the earlier conclusion that no Classic profile namespace exists was wrong.
Blizzard has also added namespaces for new Classic rulesets before — `classicann` for TBC Anniversary,
announced in a staff forum reply in January 2026 rather than in a blog post. So a Forever namespace
around launch is plausible. It is not promised, and Forever being realmless means the existing
two-segment guild route cannot be reused unchanged; Blizzard would need a new addressing scheme.

`BNET_PROFILE_NAMESPACE` should stay empty. The place to watch is the Blizzard API Discussion forum
around 4 November, which is where the previous ruleset namespaces surfaced.

The more urgent API news is in the other direction and is covered in A3: Discord removes Battle.net
connections on 22 September, and the design is already on the right side of that with one bug to fix.

## 4. What I changed during this audit

In MEE6: the Welcome & Goodbye private message was rewritten (A6); the staff quick start embed (I08) had
both Fernmelder mentions replaced and its membership line corrected to say the role is automatic; the
mod alerts (I13) and server log (I14) embeds each had their remaining mention replaced; the `!apply`
custom command was rewritten to point at the pinned guide instead of telling people to post in a
read-only channel; and the `!roles` command's line "Guild Member remains subject to staff approval" was
corrected. Three embed footers were moved to 18 September 2026. Every change was re-read after saving to
confirm it persisted.

No Discord permissions, roles or channels were changed, and nothing in the application was modified.

## 5. Suggested order of work

Before 22 September, drop the `connections` scope from the linked-role flow so the Battle.net login is
the only path (A3).

Before relying on automatic role removal, fix the roster export to include offline members and add a
shrink guard to `ingestRoster` (A2).

Then, in order: make the watcher stop losing events on a Worker outage (A4); make the addon the
authority for join and leave rather than the log text (A1); merge the queue on a timer instead of at
login; reduce MEE6's Administrator to the permissions it actually uses and move its role above Guild
Member (A5); point MEE6's audit log away from #server-log (A7); add the Guild Master role to the admin
gate (A10); and add the rank-mismatch report to #staff-chat instead of automatic officer promotion.

The smaller items in A11 and the test gaps in A12 can follow.
