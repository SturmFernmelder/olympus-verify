# Town Crier webhook source contract (.196 candidate)

This is candidate implementation support, not a live webhook receipt. No webhook was created, configured, read or executed during implementation. All provider responses in the focused test are fixtures. Source publication, secret configuration, authentic review, deployment and actual acceptance remain separate gates.

## Authority and UI

Root routes `handleTownCrierWebhook(request, env, trailingParts, originalUser, body)` from `site-news-webhook.ts` at `/api/news/editor/webhook/{preview,publish,revoke,reconcile}`. The real account is re-read from its original site session. It must be an eligible, unbanned applicant with either current site Admin access or current published `office_50` authority, including the exact current appointment map, account birth and privacy generation. The existing News switch must be on for a send. A client editor flag, typed title, nomination, ballot or remembered office is insufficient.

The saved notice is the only content source. GET `preview?id=<22-char-notice-id>&revision=<positive-int>` returns the exact title/body in a single fixed embed, a fixed destination summary, payload/configuration hashes and a signed confirmation valid for at most ten minutes, the original session and the notice's original lifetime. The preview performs no Discord mutation and stores no approval row. It is invalidated by a changed revision, deadline, account, session, appointment or configuration. It is not an authorization to create a second copy.

POST `publish` accepts exactly `{confirmation, confirm:true}`. The UI must display the content and destination and require a separate affirmative button. It must not automatically retry after a transport or ambiguous response. There is no client-supplied webhook, token, username, avatar, file, embed URL, thread, component or mention list. The payload is exactly `{embeds:[{title,description}],allowed_mentions:{parse:[]}}`. The game class icon, voting-board portraits and Treasury cosmetic roles are unrelated.

The preview result includes `enabled`, `canPublish`, `cleanupOnly`, `id`, current display `revision`, `cleanupRevision`, `cleanupDestination`, `destination:{guild,channel}`, `payload`, `payloadHash`, `configHash`, `expiresAt`, `confirmation`, `state`, `removalPending` and `uncertain`. Cleanup uses the separate retained `cleanupRevision`, never the edited notice revision; it is emitted only when descriptor and ledger purpose/channel/original clocks match in the same admitted read. Expired/deleted notices return `payload:null` rather than reconstructing an old body. Cleanup-only responses always have `canPublish:false` and `confirmation:null`. Without retained valid custody, missing/off/unqualified configuration gives HTTP409 `news_webhook_unavailable`; that is an unavailable optional connection, not proof of a delivered feature in production. A current editor can still read exact retained cleanup custody while sending or News is off, credentials are unavailable, or the notice has expired/deleted. Such responses are cleanup-only and contain no confirmation or new-send authority. A refused or previously spent revision cannot publish again even with a fresh confirmation. A later revision needs confirmed removal/refusal of its previous effect and a new preview/confirmation.

POST `revoke` and `reconcile` accept exactly `{id,revision:cleanupRevision}` and require the same current editor, original account, Origin and page-version checks. Revocation requests cleanup. Reconciliation examines only the retained known pointer; it cannot search channel history, identify an unknown send or manufacture adoption. There is no endpoint that clears unknown debt or permits retry.

## Fixed configuration and provider operations

The optional bindings are `TOWN_CRIER_WEBHOOK` (exact `{guild,channel,webhook}` JSON), `TOWN_CRIER_WEBHOOK_TOKEN` (secret) and `TOWN_CRIER_WEBHOOK_ENABLED` (literal `true`). Guild must match both serving guild IDs. A send also requires enabled serving privacy and the installed original Native admission database. No binding was set by this work. Cleanup does not require the send switch to remain on, but still requires the original fixed webhook credential/configuration to qualify.

Before a claim the backend reads the configured webhook with its token and the fixed channel with the existing bot credential. It requires incoming webhook type1, exact guild/channel/webhook IDs, and an ordinary guild text or announcement channel. Forum/media/thread destinations are refused. Both reads have bounded bodies and the existing credential fetch timeout/redirect policy. Configuration, original session, current appointment, notice bytes/revision/deadline and the News switch are checked again after those reads in the atomic claim.

The claim permits one `POST .../webhooks/<id>/<token>?wait=true`. No generic REST retry helper is used. A valid response must identify the exact channel and webhook message. Body mismatch preserves a known pointer for cleanup but does not accept publication. A lost/malformed answer remains unknown without another POST. Late known responses are recorded against the original custody claim, including when the notice changes or the actor association is erased during the wait. A changed notice or requested cleanup cannot be returned as currently accepted publication.

The official [Discord webhook API](https://docs.discord.com/developers/resources/webhook) documents incoming webhooks, `wait=true` message responses, explicit allowed-mention controls, exact-message retrieval and deletion. This implementation deliberately does not use PATCH, history scanning or thread creation.

## Existing443 custody and retention

No DDL, new table or new provider-message purpose is used. `privacy_provider_messages.purpose='notice'` remains the existing finite purpose. Its operation ID is `news_webhook_v1:<22-char-notice-id>:<42-lowercase-hex>`, 81 characters within the existing32..96 constraint. The final digest comes from the signed original proof. Embedding the existing opaque notice ID allows one indexed `site_settings` lookup in the existing cleanup page query; it contains no account ID, body or credential.

One `site_settings` key, `newsWebhook:<notice-id>`, stores a finite original descriptor: notice ID/revision, operation ID, payload hash, public destination hash, keyed credential pin, guild/channel/webhook, actor/account birth/privacy generation and original created/notice-expiry/retention dates. It stores no token or body. `privacy_provider_messages` is the sole authoritative outcome ledger; metadata does not duplicate its state. The same original admitted transaction inserts both descriptor and the claimed ledger row, and asserts the claim. An unknown transaction acknowledgement does not authorize a POST. Its claimed record can consequently require attended resolution even if no provider send occurred.

Ledger states retain existing meaning: claimed/unknown are unresolved send debt; known/cleaning are known-pointer debt; removed/refused are terminal. The original ledger retention is exactly366days from its first claim. Neither replay, reconciliation, cleanup rotation nor a new actor renews it. Unresolved custody is retained rather than treated as evidence of provider absence. A descriptor can be replaced for a later revision only after the preceding operation is removed/refused; an older unresolved operation cannot be overwritten.

The registered `news_webhook` eraser adds two logical statements to the existing serving erasure batch: mark exact own prefixed ledger rows for cleanup, then scrub the exact current descriptor's actor/birth/generation and updater. It does not clear unresolved subjects or invent removal. The own-export registry adds two reads in the same original admitted account-copy batch: an exact own count and rows ordered by key with SQL LIMIT1001. It emits at most1000 `deliveries`, plus exact `count`, `returnedCount`, `limit`, `truncated` and `complete`, and a scope statement. A count/row mismatch refuses the copy. Larger retained histories are explicitly incomplete and direct the member to attended account-copy review; no unimplemented cursor or complete-history claim is invented. Each delivered row projects only notice ID, revision, state, removal-pending and original dates. Tokens, proofs, destination/provider pointers, body and counterpart identities are withheld. This is selected current metadata, not a complete immutable publication history. The central main erasure and export physical costs must be qualified with those actual additions; unchanged443 schema does not imply unchanged statement count.

Terminal/orphaned descriptor expiry is one bounded DELETE, at most20rows per invocation, after its original366day retention, no extant notice and no unresolved matching ledger row. `newsWebhookMetadataExpiryPlan` is not silently called by this module. Root may run it only from genuine measured spare capacity inside the existing News31 statement family; its exported bound is five physical Native statements. If the family has insufficient capacity or a pending/failed Native group, expiry is deferred. There is no new cron job, larger700budget or strict expiry-completion SLA.

## Edit, expiry, removal and cost

An existing successful News edit/delete transaction adds one conditional ledger-update statement immediately after its exact original notice nonce is stored. It requests cleanup of that notice's old operation before the notice can be deleted. It does not change the existing create/replay/tombstone semantics. A signed preview for the old revision then fails its original notice predicate.

Expiry adds no News cron query. The existing provider-message page SELECT derives new-prefix cleanup eligibility when its original notice is absent, expired or a different revision; that same SELECT reads the exact descriptor by indexed key. Its existing admitted visit marks cleanup_requested without changing original retention. Unknown/claimed sends are never given a fabricated pointer by this sweep.

The new-prefix cleanup branch runs before the unchanged bot-author path. It validates the original descriptor, current keyed credential pin, incoming webhook identity and exact known message. A successful `known -> cleaning` CAS permits one DELETE. A lost DELETE stays cleaning and later invocations only GET the exact pointer to prove absence. Current-token/config drift, malformed metadata, foreign author or unavailable Discord remain held. There is no token fallback, reused bot-author proof or automatic repeated DELETE.

The isolated current443 fixture measured known webhook cleanup at four Native groups with statement counts `[2,5,5,5]` (17physical statements) and three fixture provider calls. The existing bot path is checked against that same envelope. Cleaning without proven absence uses only reads and retains debt. The unchanged News expiry sweep and its original conditional audit measured `[8,5]`; the first test incorrectly expected one group, retained its failure, then corrected that fixture accounting. These are exact local observations, not production cost or outcome claims. Root still qualifies the full current scheduled composition and actual main erasure additions.

Focused leaf: `node worker/tests/town_crier_webhook196_test.cjs`, with original installed Native admission and real isolated in-memory SQLite; only fixed Discord responses are mocked. It additionally checks current-editor cleanup reads while sending/News is off, missing-token holds, edited versus retained cleanup revisions, expired/deleted payload omission, strict descriptor/ledger matching, and1002 retained descriptors with exact count and bounded1000-row output. It checks authority/session races, confirmation grammar, body/config/revision binding, disabled gates, one effect, lost answers, Native debt, atomic mutation cleanup, expiry cost, bot-path compatibility, known-pointer ownership, own copy/scrub and terminal TTL. No provider configuration or real Discord request is part of this test.

The retained cleanup/export expansion attempts also preserve fixture failures: an expired thirty-day-old request correctly returned403; its separately renewed login initially lacked the Native-mode flag and correctly held at the recovery boundary; a raw SQLite bulk seed was correctly refused by installed admission triggers. The final fixture keeps the old-cookie403 assertion, uses the actual source OAuth issuer with Native mode selected from fixture creation, and seeds the large history through original admitted batches of at most100 statements. None of these corrections changes a production guard, original operation clock, substantive assertion or deadline.

## Attended cleanup after a notice disappears

The editor has a separate **Retained Discord cross-posts** reader. `GET /api/news/editor/webhook/retained` reauthenticates the current editor and reads at most51 original metadata keys before its custody join, inspecting50 per page. Its optional `after` is the last inspected opaque notice ID, not an authorization token. Even a page with no valid records may have a next page. Invalid descriptors are withheld and counted; the UI retains that warning across traversal rather than presenting a locally clean final page as complete history. Concurrent edits mean traversal is not a snapshot.

The list exposes only the original notice ID, cleanup revision, public guild/channel and outcome flags. It reconstructs no notice body and reveals no webhook credential, provider message pointer, original proof or counterpart identity. Sending and News may be off, and an expired or deleted notice may still have unresolved custody. Each original record opens the existing exact-revision preview. That retained reader offers cleanup only, even if a malformed or stale positive send DTO is supplied. Actual deletion still requires the original known-pointer, credential, admission and one-effect checks; an unknown send never gains an invented pointer or resend.

Treasury and webhook requests capture the original view/account liveness predicate before awaiting the shared API. A delayed401 or409 from a disposed view cannot sign out or display a reload on a later route/account. Original role-operation feedback identifies the captured member, including when the picker changes while its confirmation is pending.
